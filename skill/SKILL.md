참고)를 근거로 작성했고, 채용공고(JD) 맞춤화와 일반 작성 원칙 둘 다 다룹니다.

이력서에 들어가는 모든 사실은 아래 세 파일에서만 가져옵니다. 여기 없는 내용은 JD가

## 1. 섹션 순서 (Harvard Career Services 기준)

경력 3년 이상인 전문가는 이 순서를 따릅니다 (`SOURCES.md`의 dabydat 참고자료 근거):

1. 이름 · 연락처
2. 핵심 기술 (엔지니어링 직군은 기술을 최상단에 — 채용 담당자가 5초 안에 기술 스택부터 훑기 때문)
3. 경력 사항 (최신순)
4. 프로젝트 (관련 있으면)
5. 학력 (경력자는 맨 아래)

지금 `backup/resume/resume.md`와 `index.html`은 이미 이 순서를 따르고 있습니다 — 고칠 필요 없음.

## 2. 불릿 작성 — XYZ 공식

`[Y]로 측정되는 [X]를, [Z]를 해서 달성` — 축약하면 **행동 동사 + 한 일 + 기술적 맥락 + 비즈니스 임팩트**.

- 나쁜 예: "웹 애플리케이션 개발 담당"
- 좋은 예: "IOCP 기반 인증 서버를 개발해 PC방 관리 플랫폼의 동시접속 처리 안정성을 확보"

과거형·능동태 사용, 불필요한 "저는", "제가" 같은 1인칭 대명사 생략, 불릿 끝에 마침표
없음 (불릿은 문장이 아니라 항목이라서).

## 3. AI 시대 이력서 스크리닝에 대한 실제 사실

**오해**: "이력서 75%가 AI/ATS에 의해 사람 눈에 닿기도 전에 자동 탈락한다"
→ **근거 없음.** 이 통계는 "ATS를 이겨내는 서비스"를 팔던 업체들이 만든 수치입니다.
실제 탈락은 대부분 사람이 5~20초 훑어보고 거르는 것이지, 로봇이 점수로 자동 거르는
게 아닙니다.

**오해**: "PDF는 ATS가 못 읽는다"
→ **최신 ATS(Greenhouse, Workday, iCIMS, Lever)는 PDF를 정상적으로 파싱합니다.**
문제는 PDF라는 형식 자체가 아니라 **레이아웃용 다단(multi-column) 표**입니다 — 콘텐츠
표(예: 기술 목록)는 괜찮지만, 이력서 전체를 여러 단으로 배치하는 건 파싱 순서를
뒤섞을 수 있어 피해야 합니다. 지금 있는 `backup/resume/resume-ats.pdf`는 처음부터 단일 컬럼
구조라 이 문제가 없습니다.

**실제로 SHRM 2026 공식 리포트 기준 조직의 27%가 채용에 AI를 실제로 씁니다** — 그러니
"AI가 아예 관여 안 한다"도 사실이 아니고, "AI가 로봇처럼 자동 거른다"도 사실이 아닙니다.
사람이 최종적으로 훑어보는 시간(5~20초)에 최적화하는 게 핵심입니다.

## 4. 제출 전 체크리스트

- [ ] 이름이 한 줄에 안 잘리고 들어가는가
- [ ] 단일 컬럼, 레이아웃용 표·그래픽 없음
- [ ] 폰트는 표준 서체, 본문 최소 10.5pt
- [ ] 여백이 너무 빽빽하지도 너무 헐렁하지도 않은가
- [ ] 불릿이 마침표로 안 끝나는가
- [ ] 경력별로 도메인(업종/시스템 종류)이 드러나는가
- [ ] PDF를 텍스트 추출해봤을 때 내용이 정상적으로 나오는가 (스캔 이미지가 아닌 텍스트 기반인지 확인 — `resume-ats.pdf`는 Playwright로 직접 텍스트 추출해 확인 완료, 2026-08-05)

## 5. JD 맞춤화 절차 (채용공고가 있을 때만)

1. JD에서 필수 기술/우대 기술/핵심 업무/키워드를 표로 추출
2. 세 소스 파일과 대조해 **커버됨 / 부분 커버 / 커버 안 됨**으로 정직하게 표시
3. 회사명·직함·기간은 `backup/resume/resume.md` 원문 그대로 유지, 그 안에서 관련도 높은 불릿을 앞으로 재배치
4. 없는 내용은 절대 추가하지 않음 — 커버 안 되는 요구사항은 숨기지 않고 그대로 표시
5. `backup/job-applications/<회사>-<직무>/`에 `tailored-resume.md` + `coverage-map.md` 저장
